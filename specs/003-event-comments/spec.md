# Feature Specification: 결과 화면 댓글 기능

**Feature Branch**: `003-event-comments`

**Created**: 2026-08-09

**Status**: Draft

**Input**: User description: "기존 gender-reveal 앱(001, 002)에 댓글 기능을 추가한다. 참여자(공유 링크로
접속한 사람, 생성자 포함)는 step3(ResultReveal) 화면에서 보내는사람 이름과 내용을 입력해
댓글을 작성할 수 있다. 댓글은 로그인 없이 누구나 작성 가능하며, 한 번 작성되면 수정하거나
삭제할 수 없다(write-once). 댓글은 gender_reveal_events 테이블의 id(공유 링크 식별자)에
귀속되며, 동일한 id로 접속한 모든 사람은 동일한 댓글 목록을 최신순으로 본다.
gender_reveal_events 레코드가 만료(link_expires_at 경과)되었거나 존재하지 않는 경우
댓글 작성/조회 UI는 노출되지 않는다. 이 기능은 순수 추가 기능이며, gender_reveal_events
테이블·기존 API(/api/events, /api/events/[id])·genderRevealStore·기존 step1/step2
컴포넌트 로직에는 어떠한 변경도 가하지 않는다. 신규 댓글 테이블(gender_reveal_events.id를
외래 참조)과 신규 API 라우트(예: /api/events/[id]/comments), 신규 UI 컴포넌트만
추가하여 구현한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 결과 화면에서 축하 댓글 남기기 (Priority: P1)

공유 링크로 결과 화면(step3)에 접속한 참여자(링크를 받은 사람이든 생성자 본인이든)는 로그인
없이 보내는 사람 이름과 메시지 내용을 입력해 댓글을 남길 수 있다. 등록한 댓글은 즉시 화면에
반영되어 자신이 남긴 메시지를 확인할 수 있다.

**Why this priority**: 댓글 작성이 이 기능 전체의 핵심 가치다. 작성 기능이 없으면 조회할
댓글도, 만료 시 숨김 처리할 대상도 존재하지 않는다.

**Independent Test**: 유효한(만료되지 않은) 공유 링크로 결과 화면에 접속해 이름과 내용을
입력하고 제출한 뒤, 해당 댓글이 화면에 나타나는 것을 확인하는 것만으로 독립적으로 검증
가능하다.

**Acceptance Scenarios**:

1. **Given** 만료되지 않은 공유 링크로 결과 화면에 접속한 참여자, **When** 보내는 사람
   이름과 내용을 모두 입력하고 등록을 제출하면, **Then** 댓글이 저장되고 목록에 표시된다.
2. **Given** 결과 화면의 댓글 작성 폼, **When** 이름 또는 내용 중 하나라도 비어 있는 채로
   제출하면, **Then** 시스템은 등록을 거부하고 무엇을 채워야 하는지 안내한다.
3. **Given** 이미 댓글을 작성한 참여자, **When** 같은 화면에서 다시 입력하고 제출하면,
   **Then** 새로운 댓글로 추가 등록되며 기존 댓글은 변경되지 않는다(수정/삭제 기능 없음).

---

### User Story 2 - 모든 참여자가 동일한 댓글 목록 보기 (Priority: P2)

동일한 공유 링크(id)로 접속하는 모든 참여자는 그 링크에 달린 모든 댓글을 최신 작성순으로
동일하게 볼 수 있다. 생성자와 이후에 링크를 받은 사람 모두 같은 목록을 본다.

**Why this priority**: 댓글이 서로 공유되지 않으면 "함께 축하를 남기는" 경험이 성립하지
않는다. 작성(P1)이 갖춰진 다음 단계로서 조회가 필요하다.

**Independent Test**: 동일한 공유 링크를 두 개의 서로 다른 브라우저(또는 시크릿 창)에서
열어, 한쪽에서 작성한 댓글이 다른 쪽에도 최신순으로 동일하게 표시되는지 확인하는 것으로
독립 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 이미 댓글이 여러 개 달린 공유 링크, **When** 새로운 참여자가 그 링크로 결과
   화면에 접속하면, **Then** 기존 댓글 전체가 작성 시각 기준 최신순으로 노출된다.
2. **Given** 동일한 공유 링크를 서로 다른 사람이 각자 열람 중인 상황, **When** 한 사람이
   댓글을 새로 등록하면, **Then** 다른 사람이 해당 화면을 다시 방문(재접속/새로고침)했을
   때 동일한 순서로 그 댓글을 볼 수 있다.

---

### User Story 3 - 만료되거나 존재하지 않는 링크에서는 댓글 기능 자체를 숨김 (Priority: P3)

`link_expires_at`이 지났거나 해당 id의 레코드가 존재하지 않는 공유 링크로 접속한 경우,
댓글 작성 UI와 댓글 목록 UI 모두 화면에 노출되지 않는다.

**Why this priority**: 안전장치 성격의 요구사항으로, 댓글 기능(P1, P2)이 이미 동작하는
전제 위에서 검증할 수 있는 경계 조건이다.

**Independent Test**: 만료된 공유 링크와 존재하지 않는 id로 각각 결과 화면에 접속했을 때,
댓글 작성 폼과 댓글 목록이 화면 어디에도 나타나지 않는 것을 확인하는 것으로 독립 검증
가능하다.

**Acceptance Scenarios**:

1. **Given** `link_expires_at`이 경과한 공유 링크, **When** 참여자가 해당 링크로
   접속하면, **Then** 기존 만료 안내는 그대로 노출되고 댓글 작성/조회 UI는 나타나지 않는다.
2. **Given** 존재하지 않는 id의 공유 링크, **When** 참여자가 해당 링크로 접속하면,
   **Then** 기존 404/미존재 안내는 그대로 노출되고 댓글 작성/조회 UI는 나타나지 않는다.
3. **Given** 결과 화면을 열람 중이던 참여자, **When** 열람 도중 해당 링크가 만료되어 댓글을
   제출하면, **Then** 시스템은 제출을 거부하고 만료되었음을 안내한다.

---

### Edge Cases

- 이름 또는 내용이 공백 문자로만 채워진 채 제출되면 어떻게 되는가? (실제로는 미입력으로
  간주해 거부한다.)
- 댓글 내용이 비정상적으로 길게 입력되면 어떻게 되는가? (허용 최대 길이를 넘는 부분은
  제출 시점에 거부하고 안내한다.)
- 페이지 로드 시점에는 유효했던 링크가 댓글 제출 시점에 만료된 경우 어떻게 되는가? (제출을
  거부하고 만료 안내로 전환한다.)
- 짧은 시간에 다수의 댓글이 동시에 등록되면 목록 순서는 어떻게 결정되는가? (서버에 기록된
  작성 시각 기준으로 최신순 정렬한다.)
- 같은 사람이 여러 번 댓글을 남기거나 다른 사람의 이름을 그대로 사용해 댓글을 남기는 경우
  시스템이 이를 구분하거나 막는가? (막지 않는다. 이름은 자유 입력 텍스트이며 별도의 신원
  확인이나 중복 방지는 하지 않는다.)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 만료되지 않은 유효한 공유 링크로 결과 화면(step3)에 접속한 모든
  참여자(생성자 포함)가 로그인 없이 보내는 사람 이름과 댓글 내용을 입력해 댓글을 등록할 수
  있게 해야 한다.
- **FR-002**: 시스템은 등록된 댓글을 수정 불가능·삭제 불가능한 기록으로 영구 저장해야
  한다(write-once).
- **FR-003**: 시스템은 각 댓글을 그 댓글이 작성된 공유 링크의 식별자(id)에 귀속시켜야
  하며, 서로 다른 공유 링크의 댓글이 섞여 노출되어서는 안 된다.
- **FR-004**: 시스템은 동일한 공유 링크로 접속한 모든 참여자에게 그 링크에 달린 댓글 전체를
  작성 시각 기준 최신순(최근 작성 댓글이 먼저)으로 동일하게 보여줘야 한다.
- **FR-005**: 시스템은 참조하는 공유 링크 레코드가 만료되었거나(`link_expires_at` 경과)
  존재하지 않는 경우, 댓글 작성 UI와 댓글 목록 UI를 모두 노출하지 않아야 한다.
- **FR-006**: 시스템은 보내는 사람 이름과 댓글 내용 중 하나라도 비어 있거나 공백만 있는
  경우 댓글 등록을 거부하고 사용자에게 무엇이 누락되었는지 안내해야 한다.
- **FR-007**: 시스템은 댓글 등록 요청 시점에 해당 공유 링크가 만료되었거나 더 이상 존재하지
  않으면, 페이지가 이전에 정상적으로 로드되었더라도 등록을 거부하고 만료/미존재 상태를
  안내해야 한다.
- **FR-008**: 시스템은 댓글 작성 권한에 있어 생성자와 이후 방문한 참여자를 구분하지 않아야
  한다 — 유효한 링크에 접근한 모든 사람이 동등하게 댓글을 작성할 수 있다.
- **FR-009**: 시스템은 기존 `gender_reveal_events` 테이블, 기존 이벤트 API
  (`/api/events`, `/api/events/[id]`), `genderRevealStore`, 기존 step1/step2 화면
  로직을 변경하지 않고 이 기능을 추가해야 한다.
- **FR-010**: 시스템은 댓글 데이터를 저장하기 위해 `gender_reveal_events`의 id를
  참조(귀속)하는 별도의 신규 저장 구조를 사용해야 하며, 기존 이벤트 데이터와 분리되어
  관리되어야 한다.

### Key Entities *(include if feature involves data)*

- **댓글(Comment)**: 특정 공유 링크(젠더리빌 이벤트)에 달리는 축하 메시지. 보내는 사람
  이름, 메시지 내용, 작성 시각을 가지며, 소속된 공유 링크의 id를 통해 해당 이벤트에
  귀속된다. 한 번 생성되면 내용이 변경되거나 삭제되지 않는다. 하나의 공유 링크에는 0개
  이상의 댓글이 달릴 수 있다.
- **젠더리빌 이벤트(기존 엔티티, 참조만 함)**: 기존에 존재하는 공유 링크 단위 레코드로,
  이 기능은 그 id를 외래 참조로만 사용하고 이벤트 자체의 구조나 상태는 변경하지 않는다.
  댓글 기능의 노출 여부는 이 엔티티의 만료 상태(존재 여부, `link_expires_at`)에 종속된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유효한 공유 링크에 접속한 참여자는 결과 화면 진입 후 30초 이내에 댓글 작성을
  완료할 수 있다.
- **SC-002**: 동일한 공유 링크로 접속한 서로 다른 참여자 100%가 같은 시점에 동일한 댓글
  목록을 동일한 순서(최신순)로 본다.
- **SC-003**: 만료되었거나 존재하지 않는 공유 링크에 접속했을 때, 댓글 작성/조회 UI가
  노출되는 경우는 0%다.
- **SC-004**: 한 번 등록된 댓글은 이후 모든 열람에서 100% 동일한 내용으로 유지되며, 등록 후
  변경되거나 사라지는 경우가 없다.
- **SC-005**: 이름 또는 내용을 빠뜨리고 제출을 시도한 참여자의 90% 이상이 별도 문의 없이
  안내 메시지만으로 무엇을 고쳐야 하는지 이해하고 재제출에 성공한다.

## Assumptions

- 댓글 작성자에 대한 신원 확인(로그인, 전화번호 인증 등)은 요구되지 않으며, 보내는 사람
  이름은 참여자가 자유롭게 입력하는 텍스트다. 동일 이름 중복, 타인 이름 도용 방지 등의
  검증은 이번 범위에 포함하지 않는다.
- 보내는 사람 이름은 최대 20자, 댓글 내용은 최대 100자로 제한한다. 초과 입력 시 제출을
  거부하고 안내 메시지를 표시한다.
- 댓글 목록은 참여자가 결과 화면에 접속하거나 새로고침하는 시점에 최신 상태로 표시되면
  충분하며, 다른 참여자가 실시간(웹소켓 등)으로 화면을 보고 있는 동안 자동 갱신될 필요는
  없다.
- 댓글 수에 대한 상한이나 페이지네이션은 이번 범위에서 요구되지 않는다 — 하나의 공유
  링크에 달리는 댓글 수는 초대된 소수 인원 규모로, 전체 목록을 한 번에 보여줘도 충분하다.
- 부적절한 댓글에 대한 신고, 관리자 삭제, 욕설/스팸 필터링 등 콘텐츠 모더레이션 기능은
  이번 범위에 포함하지 않는다. write-once 정책은 애플리케이션 레벨의 사용자 기능 제한을
  의미하며, 운영/DB 차원의 예외 조치 가능 여부는 이 스펙의 범위 밖이다.
- 댓글은 step3(ResultReveal) 화면에서만 노출되며, step1(입력)·step2(인터랙션) 화면에는
  댓글 관련 UI가 추가되지 않는다.
